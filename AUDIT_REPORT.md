# Auditoría técnica de MAPEORED

**Fecha:** 2026-09-30  
**Alcance:** revisión estática de `index.html`, `assets/js/app.js`, `assets/css/styles.css`, `data/activos_mapeados.json`, `scripts/ingest.py`, `setup_proyecto.ps1`, `ROADMAP.md` y materiales de marketing. No se encontró backend, manifiesto de dependencias, configuración de despliegue ni suite de pruebas. La solicitud anuncia seis ejes, pero desarrolla cinco; se cubren todos los ejes especificados y se añade el riesgo de operación/despliegue donde corresponde.

**Dictamen:** no apto para producción enterprise ni para manejar inventario real sin remediación. La interfaz es un prototipo estático con dos implementaciones incompatibles; permite XSS desde CSV y genera PowerShell sin escapar entradas. No existe autenticación, autorización ni persistencia central. Los datos y planos del repositorio deben tratarse como información operativa sensible; no se puede afirmar que los valores visibles sean reales, pero su forma y contexto justifican protegerlos y anonimizarlos para demos.

## 1. 🚨 Hallazgos Críticos / Bloqueantes

1. **ALTO - XSS almacenado/reflejado al importar CSV.** El flujo de importación convierte filas externas en `mergeData` y construye celdas mediante interpolación dentro de `tr.innerHTML`; hostname, IP, MAC, conexión, OS e ID pueden contener HTML/JavaScript ejecutable. El `onclick` interpolado también construye código a partir de `row.id` con un escape parcial de comillas simples, insuficiente para HTML/atributos/JavaScript. Un CSV no confiable puede ejecutar código con el origen de la aplicación, leer los datos en memoria y manipular descargas o solicitudes del navegador. Evidencia: [index.html](index.html#L939), [index.html](index.html#L949), [index.html](index.html#L1047). Prioridad P0: reemplazar por `textContent`, nodos y listeners; no interpolar datos en HTML ni en manejadores inline. Añadir prueba con payloads HTML en cada columna.

2. **ALTO - Inyección de comandos en PowerShell generado.** `openPs1Modal()` concatena `hostname` y `newHostname` sin validación ni escape en argumentos entre comillas. Un valor controlable por edición/importación (tras asignar una fila importada al plano) puede cerrar la cadena e insertar comandos en el `.ps1`. La salida incluye `-Force -Restart`; su ejecución puede cambiar nombres y reiniciar equipos. No se ejecuta desde el navegador, pero es un artefacto peligroso diseñado para ejecución manual y el botón no aplica una aprobación adicional. Evidencia: [index.html](index.html#L1018), [index.html](index.html#L1028), [index.html](index.html#L1231), [index.html](index.html#L1242). P0: validar hostname con una allowlist estricta antes de guardar/exportar, escapar correctamente literales PowerShell, generar solo cambios revisados, incluir `-WhatIf`/`SupportsShouldProcess` por defecto y retirar reinicio automático.

3. **ALTO - El script descargado no corresponde al propósito declarado y tiene efectos colaterales.** La UI lo presenta como renombrado de Active Directory, pero el flujo activo produce `Rename-Computer` y `-Restart`; no implementa una operación explícita de renombrado del objeto AD ni separa aprobación, conectividad, permisos, previsualización y ejecución. Además, los datos iniciales tienen hostname actual y propuesto distintos, por lo que abrir el generador puede producir comandos para todos los registros de muestra sin que el usuario los haya editado. Evidencia: [index.html](index.html#L559), [index.html](index.html#L1231), [index.html](index.html#L1242). Bloquear el uso operativo hasta definir el comando correcto, el alcance remoto y el proceso de cambio.

4. **ALTO si se publica fuera de un entorno controlado - No hay autenticación ni autorización.** Es una página estática: cualquier visitante con acceso al sitio obtiene el inventario enviado al navegador y puede editar la copia local, borrar registros y descargar JSON o scripts. No hay backend ni rutas protegidas donde implementar permisos; CORS/CSRF no son controles aplicables a la funcionalidad actual porque no hay API de escritura. No desplegar públicamente ni considerar esto control de acceso. Si se requieren usuarios múltiples, trasladar persistencia y permisos a un backend con RBAC, autenticación corporativa y auditoría.

5. **ALTO - Exposición de información de red e instalaciones en el repositorio.** El JSON, el HTML de muestra y los planos contienen identificadores de activos, direcciones privadas, MAC, nombres de host, puertos/switches y distribución física. No encontré credenciales o tokens reconocibles en la búsqueda textual, pero esos datos también son sensibles. Confirmar si son ficticios; si no, tratarlos como datos internos, retirar su difusión y sanear fixtures. Borrar un archivo en un commit futuro no elimina su historial Git.

6. **ALTO - Dependencias remotas ejecutables sin integridad ni política de seguridad.** Tailwind Play CDN, Font Awesome remoto y Google Fonts se cargan en tiempo de ejecución; no hay SRI, CSP ni configuración de cabeceras. Un cambio/compromiso del proveedor o de la cadena de entrega impacta a todo visitante. La aplicación depende de scripts inline y atributos `onclick`, incompatibles con una CSP estricta sin refactor. Evidencia: [index.html](index.html#L7), [index.html](index.html#L8), [index.html](index.html#L10), [index.html](index.html#L553). Compilar y fijar dependencias con lockfile; servir assets propios; configurar CSP, `frame-ancestors`, HSTS (solo en HTTPS), `X-Content-Type-Options` y `Referrer-Policy` en el servidor/CDN.

7. **ALTO - Riesgo de pérdida de datos por sobrescrituras no transaccionales.** El ingestor escribe directamente sobre el mismo JSON recibido como referencia; si falla durante la escritura puede dejarlo truncado y no crea backup. El setup usa el directorio actual como raíz y vuelve a escribir JSON, CSS, JS y HTML, sin confirmación. Ejecutar el setup desde el proyecto puede reemplazar código existente; ejecutar el ingestor puede destruir datos/cambios previos. Evidencia: [scripts/ingest.py](scripts/ingest.py#L10), [scripts/ingest.py](scripts/ingest.py#L72), [setup_proyecto.ps1](setup_proyecto.ps1#L5), [setup_proyecto.ps1](setup_proyecto.ps1#L58), [setup_proyecto.ps1](setup_proyecto.ps1#L165), [setup_proyecto.ps1](setup_proyecto.ps1#L243), [setup_proyecto.ps1](setup_proyecto.ps1#L306). No ejecutar el scaffolder sobre un checkout con datos; escribir a salida temporal, validar y reemplazar atómicamente con backup y confirmación explícita.

## 2. ⚠️ Inconsistencias & Deuda Técnica

1. **Dos aplicaciones y dos esquemas incompatibles.** La implementación activa vive inline en `index.html` y usa `id/floor/top/left/hostname`; el JSON usa `box_id/piso/top_pct/left_pct/hostname_actual`; `assets/js/app.js` espera un tercer contrato basado en el JSON, pero no está enlazado. La app activa inicia con siete registros hardcodeados y no carga `data/activos_mapeados.json`; el gestor JSON exporta esa matriz inline. Por tanto, cambios/importaciones no representan la fuente de verdad del JSON versionado y los datos mostrados no corresponden necesariamente al inventario del archivo. Evidencia: [index.html](index.html#L559), [index.html](index.html#L583), [index.html](index.html#L1202), [index.html](index.html#L1220), [assets/js/app.js](assets/js/app.js#L29), [data/activos_mapeados.json](data/activos_mapeados.json#L1).

2. **El JavaScript externo no puede habilitarse simplemente con una etiqueta `script`.** Al iniciar busca `floor-selector`, pero el HTML define `floor-select`; el primer `addEventListener` sobre `null` detendría la inicialización. Los demás IDs, funciones, esquema y DOM también divergen. Además, ambos scripts declaran globals como `let activosData` y funciones con el mismo nombre; unirlos en el ámbito global produciría colisiones y/o errores de redeclaración. Evidencia: [assets/js/app.js](assets/js/app.js#L10), [assets/js/app.js](assets/js/app.js#L11), [index.html](index.html#L172), [assets/js/app.js](assets/js/app.js#L177), [index.html](index.html#L890). La solución es consolidar en módulos, no activar ambos sistemas.

3. **CSS externo huérfano y duplicación de estilos.** `index.html` no enlaza `assets/css/styles.css`; su apariencia depende de Tailwind CDN y estilos inline. El CSS y el JS externos parecen una versión anterior, no una capa compartida. Mantenerlos así crea falsas expectativas sobre qué código rige la UI. Ver [index.html](index.html#L7) y [assets/css/styles.css](assets/css/styles.css#L1).

4. **Lógica repetida y estado global.** Hay dos parsers CSV completos (uno inline y otro en el JS huérfano), normalización duplicada en `index.html` (`normalizarValor` en líneas 991 y 1194), estado mutable global, renderizado, parsing, cruces y generación de comandos en un mismo script de más de 1.200 líneas. Separar dominio/schema, parsing/validación, servicios, estado y presentación. Referencias: [index.html](index.html#L991), [index.html](index.html#L1076), [index.html](index.html#L1194), [assets/js/app.js](assets/js/app.js#L322).

5. **Cruce de datos no fiable.** La app inline une AD y UniFi por IP registrada/resuelta, pero no valida duplicados ni ambigüedades; el último registro con la misma IP gana. El cruce reemplaza `mergeData`, no la fuente `activosData`; los datos cruzados no llegan al JSON ni al script salvo que se reasignen manualmente. El ingestor Python solo itera filas UniFi y nunca agrega AD no emparejado, por lo que no genera `SOLO_AD_INACTIVO` aunque el producto lo ofrece. El ingestor preserva coordenadas por coincidencia exacta de IP y no normaliza; una IP vacía/duplicada puede asociar datos erróneamente. Evidencia: [index.html](index.html#L1140), [index.html](index.html#L1177), [scripts/ingest.py](scripts/ingest.py#L16), [scripts/ingest.py](scripts/ingest.py#L32), [scripts/ingest.py](scripts/ingest.py#L53), [scripts/ingest.py](scripts/ingest.py#L55).

6. **Edición de coordenadas incompleta.** `parseFloat(...) || valorAnterior` impide establecer coordenadas válidas en cero; no hay validación de límites, finitud ni de que posición más ancho/alto quede dentro del plano. El arrastre limita posición a 95% sin considerar la dimensión real y el redimensionado tampoco limita el borde final. Evidencia: [index.html](index.html#L751), [index.html](index.html#L754), [index.html](index.html#L841), [index.html](index.html#L870). Validar un esquema y los invariantes geométricos antes de mutar estado.

7. **Datos ficticios presentados como verificados.** `addNewHotspot()` fabrica IP y MAC aleatorias y marca el nuevo activo `VERIFICADO_ACTIVO`; el índice derivado del tamaño puede colisionar tras borrar/crear elementos. Esto contamina la evidencia operativa y el script de cambios. Evidencia: [index.html](index.html#L761), [index.html](index.html#L771). Los registros nuevos deben empezar como borrador/no verificado y usar identificadores únicos deterministas o generados con control de colisión; no inventar identificadores de red.

8. **Errores y validación débiles.** El flujo inline no maneja `FileReader.onerror`, no valida columnas requeridas ni captura fallos de parsing/cruce; archivos enormes se leen enteros en memoria. El CSV parser casero no reporta comillas mal balanceadas, filas con anchos distintos ni encabezados repetidos. En el JS huérfano se llama a `validarColumnas()` pero se ignora su resultado. El `fetch` de ese módulo no comprueba `response.ok` ni valida el esquema, y solo registra el error en consola. Evidencia: [index.html](index.html#L1051), [index.html](index.html#L1076), [assets/js/app.js](assets/js/app.js#L29), [assets/js/app.js](assets/js/app.js#L299), [assets/js/app.js](assets/js/app.js#L315).

9. **Estados y mensajes no confiables para operación.** No hay estados de carga/error visibles para inicialización de la matriz ni recuperación/reintento; errores de lectura no quedan asociados con una limpieza del estado previo. No existen Error Boundaries (no hay framework React), logging estructurado, telemetría ni auditoría de quién modificó/exportó. La interfaz es offline/local, así que no promete resiliencia de servicio ni historial.

10. **Escalabilidad de UI limitada.** Cada tecla de búsqueda filtra, ordena y vuelve a crear todas las filas (`O(n log n)` más recreación del DOM); el CSV completo y sus objetos se retienen en memoria; no hay debounce, paginación ni virtualización. Es aceptable para el pequeño fixture actual, no para exportaciones grandes. Evidencia: [index.html](index.html#L892), [index.html](index.html#L939), [index.html](index.html#L1076).

11. **Sin base para verificar CVEs o regresiones.** No hay `package.json`/lockfile, requirements/pyproject, configuración de análisis, pruebas automatizadas ni pipeline visible. No es posible inventariar CVEs de componentes transitivos ni afirmar que el producto pasa controles enterprise. No se encontraron importaciones npm o Python de terceros en los archivos inspeccionados; sí hay dependencias runtime CDN.

No borrar a ciegas: conservar la lógica útil (parseo, filtros/calibración) y trasladarla a módulos probados antes de retirar los archivos huérfanos.
2. **Eliminar la matriz inline de demostración de `index.html`.** Reemplazarla por fixture explícitamente identificado en pruebas o por carga de datos validada; evitar tener copias divergentes del inventario. Ver [index.html](index.html#L559).
3. **Eliminar el parser CSV duplicado y la segunda declaración de `normalizarValor`.** Mantener una única implementación testeada después de consolidar los módulos. Ver [index.html](index.html#L991), [index.html](index.html#L1076), [index.html](index.html#L1194), [assets/js/app.js](assets/js/app.js#L322).
4. **Retirar Tailwind Play CDN de producción y evitar dependencias remotas innecesarias.** Compilar CSS local y retirar Font Awesome/Google Fonts si no se justifican o autoalojarlos con versiones fijadas e inventariadas. Ver [index.html](index.html#L7), [index.html](index.html#L8), [index.html](index.html#L10).
5. **No borrar planos ni JSON sin confirmar clasificación y respaldo.** No se identificaron archivos basura con suficiente certeza. Los planos modificados y datos reales deben sanearse o trasladarse a almacenamiento privado, no eliminarse automáticamente del workspace o del historial.

## 4. 🏗️ Plan de Refactorización & Escalabilidad

1. **Decidir el modelo de producto antes de llamarlo enterprise.** Si solo es una herramienta offline de un operador, documentar explícitamente el límite local, no sincronizado y no multiusuario; distribuir datos sanitizados y scripts en modo revisión. Si será multiusuario/productivo, construir backend: identidad corporativa, RBAC por sede/acción, API validada, persistencia transaccional, auditoría inmutable y límites de tamaño/uso. El frontend estático por sí solo no puede garantizar control de acceso ni trazabilidad.
2. **Definir contrato versionado del activo.** Un esquema único que nombre `box_id`, `piso`, coordenadas y dimensiones, hostname actual/propuesto, estado y campos opcionales; validar JSON y CSV en frontera con tipos, límites, unicidad y compatibilidad. Migrar datos con herramienta explícita; no traducir propiedades ad hoc entre `id/floor/top` y `box_id/piso/top_pct`.
3. **Consolidar el frontend en módulos.** `index.html` solo estructura; módulos para repositorio de activos, import/export, cruce, validación, render mapa, tabla y generador de cambios. Quitar variables globales y manejadores inline para habilitar CSP estricta. Usar una capa de estado única y actualizar tabla, mapa y preview a partir de la misma fuente.
4. **Aislar operaciones peligrosas.** La UI debe preparar un plan de cambios revisable, no afirmar que aplica cambios a AD. Validar nombres contra regla de hostname, detectar colisiones y diferencias, producir script con `WhatIf` por defecto y sin reinicio; documentar permisos, aprobación, rollback y pruebas en entorno aislado. Una API nunca debe ejecutar comandos recibidos directamente desde el cliente.
5. **Rehacer ingesta con salida segura.** CLI con argumentos, validación de columnas y encoding, normalización de IP/MAC/hostname, informe de duplicados/no emparejados, preservación de registros AD-only y coordenadas por clave estable (no IP cambiante). Escribir en archivo temporal, validar salida, backup y reemplazo atómico; modo dry-run. Añadir fixture de entrada y salida reproducible.
6. **Endurecer despliegue y cadena de suministro.** Fijar versiones, lockfile, build reproducible, escaneo SCA/SAST, revisión de actualizaciones y CI. Servir HTTPS con CSP restrictiva, HSTS, `frame-ancestors`, `nosniff`, `Referrer-Policy` y políticas CORS solo si hay API y orígenes definidos. No publicar JSON/plano de clientes en CDN público.
7. **Diseñar límites de rendimiento.** Limitar bytes, filas y columnas de CSV; parsear/validar en worker si el tamaño lo justifica; filtrar con debounce y añadir paginación/virtualización cuando los volúmenes objetivo lo exijan. Medir con datasets representativos antes de optimizar.
8. **Introducir pruebas de contrato y seguridad.** Unit tests para parser, normalización, cruce, restricciones geométricas y serialización de PowerShell; pruebas de integración para importación + selección + JSON + script; prueba XSS; casos de duplicados y filas AD-only; prueba de regresión que verifica no ejecutar/reiniciar nada. Añadir validación de esquema a los datos versionados en CI.
